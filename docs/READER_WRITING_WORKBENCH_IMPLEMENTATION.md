# Reader 纸笔写作学习工作台实施文档

状态：阶段 A-E 已实施；写作、口语与范文中文均已按稳定 ID 对齐，保留 `needs_review` 供后续人工校对。
适用模块：Reader / 《В мире людей - 写作口语》/ 写作部分
对应数据：`data/textbook/writing_speaking/`
对应生成器：`scripts/convert-writing-speaking.js`

## 1. 核心结论

写作部分不应被设计成网页里的文字编辑器，也不应在当前阶段被设计成带倒计时的考试压力训练。

这一模块的定位是：**帮助学生在纸上完成一篇俄语写作，并在写前、写中和写后提供分阶段支持。**

目标学习闭环为：

> 理解材料 → 明确交际任务 → 组织想法 → 选择结构与表达 → 在纸上写作 → 自查 → 对照范文 → 修改

因此，本次实施遵守以下硬约束：

- 不添加写作文本框、在线草稿或网页内作文提交。
- 不添加倒计时、强制限时、自动交卷或考试音效。
- 原书中的“20 分钟 / 30 分钟”只作为原书信息保留，不转化为运行中的计时器。
- 不以浏览器字数统计判断学生是否完成写作。
- 范文默认折叠，且只显示与当前任务相关的范文。
- 原书任务、中文翻译、学习辅助、生成范文必须清楚标明来源，不能混为教材原文。
- 口语任务继续作为独立区域存在，不混入写作任务列表。
- 写前词汇、题目译文、范文译文和口语译文属于教辅核心内容，不得因解析或对齐升级而静默移除。
- 第四步必须提供可执行的段落职责、句型与替换槽位，不得退化为只有标题的框架列表。

未来可以单独增加“考试模式”，但考试模式不属于本次范围，也不能反向改变当前学习模式的交互。

## 2. 产品目标

### 2.1 学生完成本页后应获得什么

学生不是简单地“看过一道写作题”，而应至少完成以下学习行为：

1. 看懂题目要求、写作对象和交际目的。
2. 在纸上列出内容要点或简单提纲。
3. 从当前任务对应的结构和表达中选择可用内容。
4. 在纸上完成初稿。
5. 根据任务专属清单进行自查。
6. 对照相关范文，找到内容、结构和语言上的差距。
7. 在纸上完成修改。

### 2.2 Reader 在流程中的角色

Reader 负责：

- 呈现可靠、可追溯的原书任务。
- 帮学生把题目拆成可以执行的小步骤。
- 提供当前题型真正需要的结构、表达和自查清单。
- 记录学生对学习阶段的自我确认。
- 在合适的时机提供范文对照。

Reader 不负责：

- 代替纸笔写作。
- 假装验证学生是否真的写完。
- 自动给纸上作文评分。
- 把学习过程包装成考试过程。

## 3. 当前基线与需要解决的问题

### 3.1 学习流程问题

当前 `renderWritingSpeakingChapter()` 已移除写作文本框，但仍缺少完整的纸笔学习闭环：

- 页面能展示题目、框架、范文和评分风险，但没有把它们组织成连续的学习步骤。
- 学生可以直接“标记完成”，完成状态与构思、纸上初稿和修改无关。
- 已失效的 `rr_ws_drafts_v1`、`getWsDrafts()`、`saveWsDraft()` 和 `.ws-draft-area` 仍留在代码中。
- 原书限时以醒目的计时徽章出现，容易让学习模式产生不必要的考试暗示。
- 每道任务会重复展示整章所有范文和所有风险，信息量大且相关性不稳定。
- 框架匹配失败时会回退到第一个框架，可能给学生错误指导。

### 3.2 数据问题

当前生成数据不能直接作为新工作台的可靠输入：

- 48 个生成的“写作任务”中，至少 10 个含有 `Позвоните`、`расспросите`、`проведите беседу` 等纯口语指令。
- 19 章的 `readingMaterial` 均为空，题目前的输入材料与任务没有被稳定拆分。
- 17 个任务保留了 `来源:` 等转换痕迹。
- 有些共同情境被误识别成独立写作任务，`a)`、`б)` 选项又与共同情境断开。
- 主题 4.1 的原学习单元含正式消息和议论文任务，但生成章节没有写作或口语任务。
- 所有章节当前仍是 `needs_review`，不能在界面中暗示为已人工校订教材。

### 3.3 翻译关联问题

当前中文缓存以数组下标关联任务。转换器一旦新增、删除或重新排序任务，旧翻译就会错位：

- 主题 1.1 已出现写作任务翻译整体偏移。
- `ws-t4.3_zh.json` 和 `ws-t5.2_zh.json` 已存在跨章节内容混入。
- 框架翻译也依赖数组位置，当前渲染器还可能使用错误的循环下标取得中文框架。

因此，数据修复是界面重构的前置条件，而不是视觉调整后的补充工作。

## 4. 目标信息架构

每章保持 Reader 现有章节页结构，但写作区改为“任务列表 + 单任务学习工作台”。口语区继续独立显示。

### 4.1 章节顶部

章节顶部只提供教材上下文：

- 章节标题、主题和原书页码。
- `原书内容 / OCR 来源 / needs_review` 状态。
- 本章写作任务数量与口语任务数量。
- 本章学习记录摘要，例如“2 个写作任务中，1 个已完成纸上初稿”。

不在章节顶部放倒计时、成绩环或考试提示。

### 4.2 写作任务列表

每道写作任务显示：

- 任务标题和写作类型。
- 原书页码。
- 写作对象、交际目的等简短任务标签；只有数据可靠时才显示。
- 当前学习状态：未开始 / 已构思 / 已完成纸上初稿 / 已自查修改。
- 原书建议时间；作为弱化的来源信息显示，不使用计时器图标和动态状态。

任务默认只展开当前选择的一项，减少整章所有辅助内容同时出现造成的干扰。

### 4.3 单任务学习工作台

单任务内部采用以下固定顺序。

#### 步骤一：读懂原书任务

显示内容：

- 完整俄语任务。
- 任务所依赖的输入材料、广告、图表、信件片段或共同情境。
- 中文翻译，视觉上明确属于“学习辅助”。
- 原书页码和 OCR 审核状态。

交互规则：

- 俄语正文继续支持 Reader 的点击查词。
- 长输入材料允许折叠，但原书任务本身默认可见。
- 不把输入材料计为一个写作任务。

#### 步骤二：明确交际任务

把题目拆为学生可核对的要素：

- 写给谁：收件人或目标读者。
- 为什么写：感谢、投诉、说明、概述、论证等。
- 必须写什么：题目要求覆盖的内容点。
- 使用什么语体：正式、半正式或中性。
- 最终产出是什么：信件、消息、议论文、简历、摘要等。

这部分来自结构化数据或已审核的学习辅助。无法可靠判断的字段保持空缺并标记待审核，不凭空补全。

#### 步骤三：在纸上组织想法

提供 3 至 6 个与当前任务相关的构思问题，例如：

- 发生了什么？
- 哪些事实必须交代？
- 我的立场是什么？
- 我准备使用哪两个论据？
- 我希望对方采取什么行动？

页面只提示“请在纸上写关键词或提纲”，不提供输入框。

学生可手动勾选“已完成构思”。这个状态代表学生的自我确认，不代表系统验证了纸面内容。

#### 步骤四：选择结构与表达

只显示与当前任务绑定的内容：

- 一份匹配的输出框架。
- 按交际功能分组的可复用表达。
- 必要的连接词、开头和结尾表达。
- 容易出现的语体或语法风险。

规则：

- 找不到匹配框架时显示“当前任务暂无已审核框架”，不得回退到任意框架。
- 表达数量以够用为准，默认展示最相关的一组，其余内容折叠。
- 每条学习辅助标明“学习辅助”，不得伪装成原书答案。

#### 步骤五：在纸上完成初稿

这一步不提供网页编辑器，只显示简洁的纸笔行动提示：

> 请离开屏幕，在纸上根据提纲完成初稿。写完后回到这里继续自查。

学生完成后手动勾选“已完成纸上初稿”。

如果原书含建议时间，可以显示为“原书建议：20 分钟”，但不自动启动、倒数或提示超时。

#### 步骤六：自查

自查清单必须随任务类型变化，不能整章复用同一份“评分风险”。

通用检查项包括：

- 是否覆盖题目要求的全部内容点。
- 是否符合收件人、目的和语体。
- 段落顺序是否清楚。
- 是否有明确的开头和结尾。
- 是否检查格、体、时态、一致关系、拼写和标点。

题型专属检查示例：

- 投诉信：事实、造成的不便、明确诉求、正式语体。
- 感谢信：感谢对象、具体原因、积极评价、得体结尾。
- 消息或摘要：信息来源、主要结论、关键数据、不过度加入个人观点。
- 议论文：问题、立场、论据、不同观点、结论。
- 简历或说明：信息完整、格式一致、事实表达准确。

学生完成纸面修改后勾选“已完成自查修改”。

#### 步骤七：对照范文并再次修改

范文默认折叠，并显示明确说明：

> 以下内容为生成的学习辅助，不是原书标准答案。建议先完成纸上初稿再查看。

行为规则：

- 不硬性锁定范文，避免把学习模式变成考试模式。
- 只显示通过 `taskId` 明确关联到当前任务的范文。
- 范文与中文翻译成对显示，但中文默认折叠，避免打断俄语阅读。
- 提供三项对照提示：我漏了什么、我可以借用什么结构、我需要改正什么语言问题。
- 不把“打开范文”自动记为完成。

## 5. 学习状态与完成语义

### 5.1 任务状态

每道写作任务保存三个独立布尔状态：

```json
{
  "planningDone": true,
  "paperDraftDone": true,
  "revisionDone": false,
  "updatedAt": "2026-08-06T12:00:00.000Z"
}
```

对应界面文字：

- 已完成构思
- 已完成纸上初稿
- 已完成自查修改

不保存作文正文、字数或纸面照片。

### 5.2 localStorage

新增独立键：

```text
rr_ws_learning_progress_v1
```

建议结构：

```json
{
  "ws-t1.1-w01": {
    "planningDone": true,
    "paperDraftDone": true,
    "revisionDone": false,
    "updatedAt": "2026-08-06T12:00:00.000Z"
  }
}
```

迁移原则：

- 不把旧 `rr_ws_drafts_v1` 中的网页文字草稿自动解释为已完成纸上写作。
- 旧键先停止写入；确认没有其他页面依赖后再删除读取逻辑。
- 不触碰通用写作模块使用的 `russian_b2_writing_drafts_v1`、`russian_b2_writing_versions_v1` 等键。
- 新键加入 `docs/数据存储说明.md`，说明所有权、字段、读写位置和清除策略。

### 5.3 章节完成

章节完成不能再与学习活动完全无关。

默认规则：

- 至少有一道写作任务被学生确认“已完成纸上初稿”，才启用“完成本章学习”。
- `revisionDone` 未完成时可以结束本章，但界面应提示“初稿已完成，自查修改尚未完成”。
- 如果本章没有可用写作任务，只显示数据待修复状态，不要求学生完成不存在的写作。
- 口语任务的完成规则不在本阶段改动，也不用于伪造写作完成状态。

这个规则只依赖学生的自我确认，不声称系统验证了纸面产出。

## 6. 数据契约

### 6.1 写作任务

每道任务必须拥有稳定 ID，并将共同情境、输入材料和实际产出指令分开。

建议结构：

```json
{
  "id": "ws-t1.1-w01",
  "kind": "writing",
  "type": "жалоба",
  "title": "Жалоба директору турфирмы",
  "sourcePage": 13,
  "sourceStatus": "needs_review",
  "contextRef": "ws-t1.1-context-03",
  "prompt": "Напишите жалобу на имя директора турфирмы.",
  "requirements": [],
  "audience": "директор турфирмы",
  "purpose": "жалоба и требование принять меры",
  "register": "formal",
  "choiceGroup": "ws-t1.1-choice-01",
  "choiceMode": "one-of"
}
```

其中：

- `id` 是进度、翻译、框架、范文和测试的共同主键。
- `contextRef` 指向共享情境，避免把“Вы с друзьями ездили...”误判成独立任务。
- `choiceGroup` 表示 `a)`、`б)` 等替代任务关系。
- `sourceStatus` 保留 OCR 或人工审核风险。
- `audience`、`purpose`、`register` 只在可从原任务可靠判断时生成。

### 6.2 输入材料

输入材料使用独立集合，不进入 `writingTasks` 计数：

```json
{
  "id": "ws-t1.1-context-03",
  "type": "situation",
  "text": "Вы с друзьями ездили в недельную поездку...",
  "sourcePage": 13,
  "sourceStatus": "needs_review"
}
```

广告、调查结果、图表、信件片段和共同题干也采用相同原则。

### 6.3 学习辅助关联

框架、范文和风险必须显式声明适用任务：

```json
{
  "id": "ws-t1.1-framework-complaint",
  "origin": "generated_study_support",
  "appliesToTaskIds": ["ws-t1.1-w01"],
  "title": "Жалоба",
  "steps": []
}
```

禁止以下行为：

- 以数组下标猜测适用任务。
- 匹配失败时取第一份框架。
- 在每道任务下重复整章所有范文。
- 将生成范文标成原书内容或标准答案。

## 7. 转换器修复方案

`scripts/convert-writing-speaking.js` 的修复先于 UI 实施。

### 7.1 解析顺序

转换器应按以下顺序处理学习单元：

1. 解析 Markdown 标题层级和 frontmatter。
2. 识别中文与俄文标题，包括“写作任务”“口语任务”“输入材料”“原书任务”。
3. 从每个区块中拆出来源元数据、共同情境、材料和输出指令。
4. 根据实际指令动词分类写作或口语，不只根据章节标题关键词分类。
5. 识别 `a)`、`б)`、编号任务及 `Задание` 块。
6. 为任务、情境和学习辅助分配稳定 ID。
7. 生成章节 JSON，并运行语义验证。

### 7.2 分类原则

写作指令示例：

- `Напишите...`
- `Составьте письменное сообщение...`
- `Изложите в письменной форме...`
- `Подготовьте резюме / аннотацию...`

口语指令示例：

- `Позвоните...`
- `Расспросите...`
- `Проведите беседу...`
- `Примите участие в диалоге...`
- `Выскажите своё мнение...`，当上下文明确要求口头回答时。

同一区块同时含书面和口头任务时必须拆分；无法确定时保留原文并标记 `needs_review`，不能静默塞入写作数组。

### 7.3 清洗边界

允许清除：

- `来源:` 等转换元信息。
- Markdown callout 标记。
- 与任务无关的页眉、页脚和 OCR 控制字符。

不允许改写：

- 任务动词。
- 否定词、数量、比例、时间和对象。
- `a)`、`б)` 的选择关系。
- 原书材料与题目之间的引用关系。

## 8. 中文翻译契约

翻译缓存改为按稳定 ID 保存，不再按数组下标保存。

建议结构：

```json
{
  "chapterId": "ws-t1.1",
  "tasks": {
    "ws-t1.1-w01": {
      "promptZh": "请给旅行社经理写一封投诉信。",
      "requirementsZh": []
    }
  },
  "contexts": {
    "ws-t1.1-context-03": {
      "textZh": "您和朋友参加了一次为期一周的旅行……"
    }
  },
  "frameworks": {},
  "modelAnswers": {}
}
```

迁移时必须：

1. 根据俄文原文重新核对现有中文，而不是机械搬运旧数组。
2. 检测翻译中的跨章节专名、题型和主题泄漏。
3. 检测源任务有 ID 而翻译缺失、翻译有 ID 而源任务不存在的情况。
4. 对不确定翻译保留 `needs_review`，不强行标记完成。

## 9. 技术修改边界

建议修改或新增：

- `scripts/convert-writing-speaking.js`：任务分类、输入材料拆分、稳定 ID 和关联字段。
- `scripts/translate-ws.js`：按 ID 生成和应用翻译。
- `data/textbook/writing_speaking/ch0000.json` 至 `ch0018.json`：重新生成并审核。
- `data/textbook/writing_speaking/ws-t*_zh.json`：迁移为 ID 映射并修正错位内容。
- `js/russian-b2/writing-session.js`：纯状态归一化、读取和保存逻辑。
- `css/reader-writing-workbench.css`：写作工作台布局、状态和响应式样式。
- `reader.html`：教材上下文接入、任务渲染入口和事件绑定。
- `tests/russian-b2/`：数据语义、状态和渲染测试。
- `docs/数据存储说明.md`：登记新 localStorage 键。

不修改：

- OCR 原始文件、PDF 和已封存源材料。
- 通用写作模块的草稿、版本和考试状态。
- Reader 阅读与语法模块已经稳定的学习逻辑。
- 听力工作台、词汇页、番茄钟和云同步敏感配置。

## 10. 视觉与交互规范

设计判断：这是面向 B2 学习者的现有学习产品改造，应保持安静、学术、工具化，与 Reader 既有主题一致。

设计参数：

- `DESIGN_VARIANCE: 4`
- `MOTION_INTENSITY: 2`
- `VISUAL_DENSITY: 6`

具体要求：

- 使用 Reader 现有 CSS 变量和明暗主题，不引入新的前端框架。
- 页面以连续学习步骤为主，不把每个提示都做成独立装饰卡片。
- 不使用考试红色、动态倒计时、脉冲提醒或成绩仪表盘。
- 俄语原文在字号、行高和字体上保持可长时间阅读。
- 中文说明弱于俄语原文，生成内容必须有稳定的来源标签。
- 学习阶段使用复选状态，不用百分比进度条伪造掌握程度。
- 展开和收起只使用轻量过渡，并遵守 `prefers-reduced-motion`。
- 图标使用项目现有图标方案；可访问名称不能只依赖图标或颜色。

### 10.1 响应式

桌面端：

- 主阅读列保持约 760 至 900px，避免俄语长行过宽。
- 任务导航和学习步骤可以使用两列辅助布局，但原书正文保持单列。

移动端：

- 在 `360x800`、`390x844`、`412x915`、`430x932` 验证。
- 所有步骤改为单列。
- 长俄语单词、任务标题和按钮文字不得溢出。
- 主要点击目标至少 44px。
- 底部章节导航不能遮挡最后一个自查项。

### 10.2 无障碍

- 学习阶段使用原生 checkbox 或等价可访问控件。
- `details/summary` 必须具有清晰标题和展开状态。
- 键盘可以完成任务切换、折叠、查词和状态确认。
- 更新状态后使用简短的非打断式反馈，不强制移动焦点。
- 颜色不是区分“未开始 / 已完成”的唯一方式。

## 11. 测试与验收

### 11.1 数据语义测试

必须新增以下断言：

- 主题 4.1 至少生成一项真实写作任务。
- 写作任务中不出现纯口语输出指令；混合任务必须被拆分或标记待审核。
- 共同情境和输入材料不计入写作任务数量。
- 所有写作任务均有唯一、稳定的 `taskId`。
- 所有翻译通过 `taskId` 关联，不使用数组位置作为唯一依据。
- 不存在翻译指向其他章节任务的情况。
- 所有框架和范文的 `appliesToTaskIds` 指向真实任务。
- 生成内容均带有 `generated_study_support` 或等价来源标记。

### 11.2 状态测试

- 未有记录时，三个阶段均为未完成。
- 勾选状态后刷新页面仍保留。
- 更新一项任务不会修改同章其他任务。
- 损坏的 localStorage JSON 不会使 Reader 崩溃。
- 旧 `rr_ws_drafts_v1` 不会自动变成纸上初稿完成记录。
- 没有任何纸上初稿记录时，章节完成按钮不可直接制造完成状态。

### 11.3 渲染测试

- 写作区域实际渲染结果中不存在 `textarea` 或作文文本输入框。
- 页面实际渲染“已完成构思 / 已完成纸上初稿 / 已完成自查修改”控件。
- 原书时间只显示为静态来源信息，不存在运行中的 timer。
- 每道任务只显示与自己关联的框架、风险和范文。
- 无匹配框架时显示空状态，不回退到第一份框架。
- 范文默认折叠，且带有非原书内容说明。
- 阅读、语法和口语区域不因写作重构发生结构回归。

当前只搜索 CSS 字符串或函数名的静态测试不足以证明控件真的被渲染，需改为执行渲染函数或使用浏览器 DOM 断言。

### 11.4 浏览器验收

至少验证：

- 桌面 `1440x900`。
- 笔记本 `1280x720`。
- 移动端 `390x844`。
- Reader 两套现有主题。
- 有输入材料、无输入材料、单任务、多任务、替代任务、无已审核框架六类章节。

检查内容：无横向溢出、无文字遮挡、折叠状态清楚、状态刷新后保留、查词可用、范文不会错误重复。

## 13. 风险控制

- 工作区已有用户修改；实施时只做窄范围补丁，不覆盖 `reader.html` 和测试中的既有差异。
- 转换器重跑会批量修改 19 个章节和翻译缓存；提交前必须用数据测试和人工抽样同时检查。
- 稳定 ID 一旦用于本地进度后不可随意变化；生成规则变更必须提供迁移表。
- 不为追求“全通过”而清除 `needs_review`；OCR 不确定性属于真实数据状态。
- 纸上写作无法由浏览器客观验证；界面必须称为“学习记录”或“自我确认”，不能称为已提交作文。
- 范文可能影响学生独立构思，因此默认折叠并给出查看建议，但学习模式不做硬锁。

## 14. 完成定义

只有同时满足以下条件，本次重构才算完成：

- 学生可以按照七步流程完成一次纸笔写作学习。
- 页面没有作文输入框，也没有运行中的考试计时器。
- 原书任务、输入材料、中文翻译和生成辅助来源清楚。
- 写作与口语任务分类可靠，已知错位数据已修复。
- 翻译、框架、风险和范文均通过稳定 ID 关联到具体任务。
- 学生可以记录构思、纸上初稿和自查修改三个阶段。
- 章节完成不再与纸笔写作活动完全无关。
- 桌面、笔记本和移动端均无布局、主题或可访问性回归。
- 阅读和语法模块不受影响。

## 15. 未来考试模式边界

未来若增加考试模式，应作为独立模式和独立状态实现，可能包含：

- 倒计时。
- 限制查词和隐藏学习辅助。
- 统一开始与结束。
- 考后复盘和评分量表。

考试模式不得复用 `rr_ws_learning_progress_v1` 表示考试成绩，也不得把学习模式默认切换为压力训练。当前纸笔学习工作台始终是默认入口。
