# 浏览器到本机 SQLite 双写与迁移方案 v1

> 状态：第一阶段已确认设计
> 前置契约：[`VOCABULARY_EVENT_CONTRACT_V1.md`](./VOCABULARY_EVENT_CONTRACT_V1.md)
> 算法契约：[`VOCABULARY_MASTERY_SCHEDULING_CONTRACT_V1.md`](./VOCABULARY_MASTERY_SCHEDULING_CONTRACT_V1.md)
> 当前实施：Phase 4 已在用户确认后启用；Phase 4.1 的损坏隔离、已验证备份自动恢复、第二位置副本和运行状态显示已完成代码与临时环境验收
> 未来边界：本方案只选择本机第一版技术，不选择云厂商、正式服务器数据库、账号或鉴权方案

## 1. 大白话结论

一次查词或复习完成后，先放进浏览器自己的“保险箱”，页面确认保存；随后浏览器把同一条记录送到电脑上的 SQLite 数据库。SQLite 是一个单文件数据库，适合当前只有一个学习者、希望以后能备份和迁移的阶段。

```text
学习行为
  ↓
浏览器 IndexedDB：事件 + 待同步记录一次写成
  ↓                         ↘ Node 没启动：继续学习，稍后再送
更新当前页面和旧 localStorage
  ↓
同源批量提交给本机 Node
  ↓
SQLite 一个事务完成校验、去重和提交
  ↓
浏览器收到同步确认，移出待同步队列
```

浏览器不是临时草稿，SQLite 也不能拿旧数据覆盖浏览器。二者保存的是同一批拥有全局事件编号的事实。

## 2. 现有系统盘点

### 2.1 可以复用

- Reader 和 Vocabulary 已共用 `vocabulary-review-records`，保存后可立即互相读取；
- `StudyActivityStore` 已能在 `belye_nochi_activity` IndexedDB 保存活动，并在 IndexedDB 不可用时退回 localStorage；
- 完整学习档案已经支持 localStorage、录音 IndexedDB、导入校验、合并和失败回滚；
- `AppRuntime` 已把不同运行环境的网络能力隔离在适配层；
- 当前 Node 版本为 24，已经实际确认可使用内置 `node:sqlite`，无需引入原生 SQLite 扩展包。

### 2.2 不能直接当新总账

- `/api/vocab-sync` 只把每日复习、掌握、到期和连续天数写进 `study-log.json`，没有逐次事件；
- `/api/novel-vocab` 把词写成 Markdown，使用随机文件名和按词面去重，不具备事件幂等性；
- `rr_sync_fail_queue` 只保存待写 Markdown 的词条载荷，没有 `eventId`，不能安全去重；
- `vocabulary-review-records` 是会被覆盖的当前投影，不是不可变历史；
- `belye_nochi_activity` 允许原地更新会话和撤回标记，契约也不同，不能直接伪装成词汇学习事件；
- 当前完整 JSON 档案没有包含 `belye_nochi_activity`。

因此，新事件通道与旧汇总、Markdown 笔记同步并行存在，核对完成后再逐步替换旧职责，不能改名后冒充已经迁移。

## 3. 第一版固定选择

| 项目 | 决定 |
| --- | --- |
| 本机数据库 | SQLite，由 Node 24 内置 `node:sqlite` 访问 |
| 数据库位置 | `%LOCALAPPDATA%\BelyeNochi\learning\white-night-learning.sqlite3` |
| 测试覆盖位置 | 可通过 `BELYE_NOCHI_DATA_DIR` 指定临时目录；生产默认不放进 Git 仓库 |
| 浏览器事件库 | `belye_nochi_learning` IndexedDB，当前版本 2；版本 2 只为既有事件增加释义索引 |
| 事件编号 | `crypto.randomUUID()` 生成 UUIDv4；生成后永久不变 |
| 学习者编号 | 首次使用生成 UUIDv4；归档迁移时保留同一学习者身份 |
| 设备编号 | 每个浏览器资料生成 UUIDv4；导入档案不能覆盖当前设备编号 |
| 发送批量 | 浏览器每批最多 100 条；接口硬上限 200 条、1 MiB |
| 写入策略 | 整批原子写入；一条无效则整批不提交 |
| 重试间隔 | 立即、5 秒、15 秒、1 分钟、5 分钟，之后最多每 30 分钟一次 |
| SQLite 日志 | WAL 模式、`synchronous=FULL`、外键开启、忙等待 5 秒 |
| 自动备份 | 保留最近 7 份每日备份和 4 份每周备份，均带 SHA-256 校验值 |
| 切换验收 | 365 天显式虚拟时间逐日对账、重启与完整重放、故障恢复和回滚全部通过；不再强制等待 3 或 14 个真实学习日 |

`BELYE_NOCHI_DATA_DIR` 是启动程序前提供的配置值，只用于测试或将数据目录放到用户明确选择的位置。第一阶段页面不暴露这个设置。

本方案没有选择未来服务器的 PostgreSQL、MySQL 或其他数据库。未来服务器只需接受同一事件契约，SQLite 数据可以按事件逐条迁移。

## 4. 谁在什么时候是权威

### 4.1 事实权威

不可变学习事件始终是事实权威，localStorage、页面统计和 FSRS 状态都是投影。

- 事件成功进入浏览器 IndexedDB 后，这次学习行为已经保存；
- 尚未收到 SQLite 确认时，它是“待同步事件”，仍然有效；
- SQLite 提交后，它成为“已确认事件”；
- SQLite 旧投影不得覆盖浏览器中较新的待同步事件；
- 发生冲突时保留双方，停止自动合并并显示可诊断错误。

### 4.2 分阶段权威

| 阶段 | 浏览器 | SQLite | 页面读取 |
| --- | --- | --- | --- |
| 影子写入 | 当前事实来源和兼容投影 | 只接收副本并核对 | 继续读现有浏览器进度 |
| 双算核对 | 保存事件和离线待同步 | 重放事件并生成对照投影 | 仍读浏览器，后台比较结果 |
| 本机总账 | 保存完整离线副本和待同步事件 | 已确认事件的耐久总账 | 浏览器投影即时显示，启动时与总账对账 |

“SQLite 成为总账”不表示浏览器可以删除所有事件。浏览器必须保留完整事件账，以便离线使用、重建投影和数据库灾难恢复。

## 5. 浏览器 IndexedDB 结构

数据库：`belye_nochi_learning`，当前版本 2。版本 2 保留版本 1 的全部对象仓库和事件，只为 `events` 增加 `senseId` 索引。

| 对象仓库 | 主键 | 内容 |
| --- | --- | --- |
| `events` | `eventId` | 完整、不可变的学习事件 |
| `outbox` | `eventId` | 待发送状态、尝试次数、下次尝试时间和最后错误代码 |
| `syncReceipts` | `eventId` | SQLite 提交时间、批次编号和内容校验值 |
| `projections` | `projectionKey` | 当前词条、复习单元和统计的可重建缓存 |
| `projectionCheckpoints` | `projectionName` | 投影版本、已处理事件数和重建校验值 |
| `migrationSnapshots` | `snapshotId` | 旧数据原始快照、来源键、校验值和迁移状态 |
| `meta` | `key` | 学习者编号、设备编号、数据库版本和最近同步状态 |

创建一条新事件时，`events` 和 `outbox` 必须在**同一个 IndexedDB 事务**中写入。任何一个写入失败都整体失败，不更新兼容 localStorage，也不显示“已保存”。

事件写入成功后才更新 `projections` 和过渡期 localStorage。投影更新失败时事件仍然安全，页面显示“已保存，显示状态待修复”，并在下次启动时从事件重建；不能反过来删除事件迁就旧进度。

## 6. SQLite 物理结构

第一版只建立事件总账和可重建缓存，不急着把每一种学习业务拆成大量表。

### 6.1 `learning_events`

| 字段 | 用途 |
| --- | --- |
| `event_id` | 主键，对应 `eventId` |
| `schema_name`、`schema_version` | 契约识别与升级 |
| `learner_id`、`device_id` | 单用户预留和设备来源 |
| `event_type` | 事件类型索引 |
| `occurred_at`、`recorded_at`、`received_at` | 发生、浏览器保存和总账接收时间 |
| `source_module` | Reader、Vocabulary、migration 等 |
| `lexeme_key`、`unresolved_lexeme_id` | 正式词元或待确认对象索引 |
| `sense_id`、`review_unit_id` | 释义和复习单元索引 |
| `content_hash` | 去重和冲突检测 |
| `event_json` | 完整规范化事件 JSON，SQLite `json_valid` 校验 |

事件 JSON 只追加，不原地修改。`receivedAt` 是接收元数据，不参与来源内容校验值；普通更正仍通过新的 `evidence_corrected` 事件完成。

### 6.2 支撑表

| 表 | 用途 |
| --- | --- |
| `schema_migrations` | 记录数据库结构升级，禁止靠猜测当前版本 |
| `ingest_batches` | 记录批次编号、设备、数量、提交时间和批次校验值 |
| `projection_records` | 保存可重建的词条和 FSRS 投影缓存 |
| `projection_checkpoints` | 记录投影版本、事件数量和源事件校验值 |
| `migration_snapshots` | 保存旧 localStorage / IndexedDB 的迁移前快照和映射摘要 |
| `backup_catalog` | 记录备份文件、SHA-256、大小、创建时间和验证结果 |

大体积录音不进入 `learning_events.event_json`。第一阶段继续留在现有录音 IndexedDB，事件只引用录音编号；以后迁移录音时另设计文件存储，不把二进制塞进 SQLite 事件表。

## 7. 本机事件接口

### 7.1 写入接口

```text
POST /api/learning-events/batch
Content-Type: application/json
```

请求：

```json
{
  "schema": "belye-nochi-event-batch",
  "schemaVersion": 1,
  "batchId": "uuid",
  "deviceId": "uuid",
  "events": []
}
```

成功响应只在 SQLite `COMMIT` 完成后返回：

```json
{
  "ok": true,
  "batchId": "uuid",
  "committedAt": "2026-08-16T12:00:00.000Z",
  "acceptedEventIds": [],
  "duplicateEventIds": []
}
```

相同 `eventId` 和相同来源内容再次提交属于正常重试，放入 `duplicateEventIds` 并视为成功。相同 `eventId` 但内容不同返回 `409 EVENT_ID_CONFLICT`，整批不写入。校验失败返回 `422 BATCH_VALIDATION_FAILED`，整批不写入。

### 7.2 状态接口

```text
GET /api/learning-store/health
```

只返回数据库是否可写、结构版本、最近提交和最近备份时间，不返回词汇、句子、写作或其他个人内容。

第一阶段不提供“上传整份进度”接口，也不提供任意 SQL、文件路径或数据库下载接口。

## 8. 同步时序

### 8.1 正常写入

1. 页面生成事件、`eventId`、`learnerId` 和 `deviceId`；
2. 完整校验事件；
3. IndexedDB 同一事务写入 `events` 和 `outbox`；
4. 更新浏览器投影和过渡期 localStorage；
5. UI 显示“已保存到本机浏览器”；
6. 同步器按最多 100 条组成批次；
7. Node 校验整批、规范化 JSON、计算 SHA-256；
8. SQLite 单一事务插入批次和事件，重复事件不重复计数；
9. SQLite 提交后 Node 返回同步确认；
10. 浏览器同一事务写入 `syncReceipts` 并从 `outbox` 删除对应事件；
11. UI 的同步状态更新为“本机数据库已备份”。

### 8.2 响应丢失

如果 SQLite 已提交但响应在网络中断前没有到达，浏览器保留待同步记录并重发。Node 根据 `eventId + content_hash` 返回“已经存在”，浏览器随后正常确认，不会重复查词或重复计分。

### 8.3 重试触发

除递增时间间隔外，下列情况立即尝试：

- 页面启动并完成本地库检查；
- 浏览器从离线恢复在线；
- 页面重新回到前台；
- 新事件进入空的待同步队列；
- 学习者在“我的”页面手动点击重试。

永久校验错误不无限重试。它进入“需要修复”状态，保留事件和错误原因，但不能阻塞其他合法批次；同步器应把故障事件隔离后重新分批验证。

## 9. 旧数据迁移

### 9.1 迁移前

1. 生成当前完整 JSON 学习档案；
2. 校验档案能够重新读取；
3. 为每个准备迁移的 localStorage 键和 IndexedDB 库计算记录数与 SHA-256；
4. 保存迁移清单，不删除任何旧数据；
5. 任何一步失败都停止迁移。

### 9.2 Vocabulary

- `vocabulary-review-records` 原样进入迁移快照；
- 可靠识别的词条映射到正式 `lexemeKey`，歧义进入待确认；
- 旧 `mastery/history/interval` 只进入旧状态快照，不伪造逐次复习事件；
- 按算法契约分散到 1–30 天渐进校准；
- 从迁移完成后的新行为开始产生真实词汇事件。

### 9.3 Reader 和活动记录

- Reader 现有位置、书签、答题、写作和听说进度继续作为兼容投影保留；
- 能确认真实发生时间和原始答案的记录可以在后续专门映射，不满足条件的只做迁移快照；
- `belye_nochi_activity` 以独立 `studyActivity` 档案模块进入新版完整档案，不能直接改名为词汇学习事件；
- `StudyActivityStore.retract()` 的旧撤回语义保留在活动快照中，新词汇证据更正遵循追加事件契约。

### 9.4 旧同步队列和服务端文件

- `rr_sync_fail_queue` 继续只负责 Markdown 笔记补写，不能转换成已发生的查词事件；
- `study-log.json` 作为历史每日汇总保留，不能反推逐次复习；
- 已生成的小说词汇 Markdown 可作为来源资料，但不能仅凭文件存在伪造“学习者已加入生词本”事件。

API Key、同步临时错误日志、缓存、数据库 WAL 文件、备份目录和设备上的当前 `deviceId` 不能进入可携带档案。历史事件中的来源设备编号保留，导入后当前设备生成自己的编号。

## 11. 加速影子核对门槛

软件正确性不再依赖等待 3 或 14 个真实学习日。SQLite 和 FSRS 只有在独立临时数据库、独立浏览器账本和显式虚拟日期中完成 365 天逐日核对，并同时满足以下条件，才具备进入受保护切换的技术条件：

1. 浏览器待同步事件最终全部得到确认，没有静默丢失；
2. 浏览器与 SQLite 按事件类型、日期、词元和复习单元统计数量一致；
3. 随机抽查和全量内容校验值一致；
4. 重复提交没有产生重复事件或重复 FSRS 更新；
5. 浏览器和 SQLite 用同一事件、算法版本及参数重算的 FSRS 状态一致；
6. Node 停机、重启和端口不可用期间，Reader 与 Vocabulary 仍能保存并刷新恢复；
7. 断网或响应丢失后可以自动补交；
8. 至少完成一次服务重启和独立空库恢复，并与恢复前事件数和校验值一致；
9. 至少完成一次 JSON v2 导出、清空测试环境、导入恢复；
10. 旧 localStorage 和 IndexedDB 数据仍然存在，可关闭新通道回到旧页面行为。

2026-08-17 已使用 2023-03-02 至 2024-02-29 的 365 个虚拟学习日完成上述核对。每个模拟日都比较浏览器与 SQLite 的事件数、来源哈希、状态哈希、稳定期、难度和下次复习日期，并覆盖刷新、Node 重启和完整重放。

真实学习日回执继续保留为生产观察信号，但不再是阻止软件切换的硬门槛。虚拟测试只能证明程序在给定事件下计算一致，不能证明默认 FSRS 参数已经针对个人训练完成。个人参数仍必须满足算法契约中的至少 1000 次合格复习、覆盖至少 90 天等条件。

## 12. 备份与恢复

### 12.1 自动备份

- 每天第一次成功提交后，如果距离上次每日备份已满 24 小时，创建一致性备份；
- 保留最近 7 份每日备份和 4 份每周备份；
- 备份写入临时文件，完成 SQLite 校验和 SHA-256 后再原子改名；
- 主备份目录默认位于数据库目录下的 `backups`；
- 已完成恢复验证的备份会复制到第二位置。Windows 正式环境优先使用 `E:\Desktop\BelyeNochi-Backups`，也可通过 `BELYE_NOCHI_SECONDARY_BACKUP_DIR` 明确指定；测试数据库只使用各自临时目录；
- 第二位置仍是本机文件，不自动上传云盘，也不代表异地容灾。

实施状态（2026-08-17，Phase 3.5）：已实现。在线备份使用 Node 内置 SQLite 备份接口，不直接复制可能仍带 WAL 的数据库文件。每日第一次成功事件提交会检查 24 小时间隔；每满 7 天补一份周备份。临时文件先通过 `PRAGMA integrity_check` 和 SHA-256 校验，再原子改名并登记到 `backup_catalog`。自动保留 7 份每日和 4 份每周备份；备份失败不撤销已提交的学习事件，但会让切换体检保持未通过。

### 12.2 启动检查

目标恢复流程如下。Node 启动时检查数据库结构版本和 `PRAGMA integrity_check`。如果损坏：

1. 立即停止数据库写入，但不阻断浏览器本地学习；
2. 关闭数据库，将损坏文件移动到带时间戳的隔离位置，不直接删除；
3. 从最新一份通过校验的备份恢复；
4. 浏览器重新提交恢复点之后缺少的事件；
5. 再次比较事件数量和校验值；
6. 未全部恢复前明确显示“数据库恢复中”，不能谎报同步成功。

Phase 4.1 已实现启动前自动恢复。每份通过独立恢复演练的备份会生成数据库之外的验证清单，记录 SHA-256、大小、事件数、来源哈希、状态哈希和验证时间，并复制到第二位置。启动时只有 `PRAGMA integrity_check` 失败且至少找到一份清单、文件哈希、SQLite 完整性和投影哈希全部一致的备份，才会执行替换。损坏的主库及其 WAL/SHM 文件先移动到带时间戳和随机编号的 `quarantine` 隔离目录，不删除；恢复中途失败会把隔离移动回滚。找不到可信备份时保持原文件不动并停止数据库启动，防止空库覆盖。恢复成功后浏览器按原事件编号补交恢复点之后的事件，再走既有哈希核对。

### 12.3 数据库结构升级

每次结构升级前自动备份。迁移在 SQLite 事务中完成；失败则回滚结构并继续使用旧版本。应用代码必须同时保留关闭新同步通道的开关，不能要求用户删除数据库解决问题。

## 13. 本机接口安全

当前 `server.js` 监听 `0.0.0.0`，意味着同一局域网可能访问静态页面。新的学习数据接口因此必须额外限制：

- 只接受来自回环地址的连接，即当前电脑自己的 `127.0.0.1` 或 `::1`；
- 校验 `Origin` 与当前 `localhost` / `127.0.0.1` 端口同源；
- 只接受 `Content-Type: application/json`，不允许表单或纯文本绕过浏览器预检；
- 不返回 CORS 允许头，不接受任意网页跨域写入；
- 学习事件批次限制为 1 MiB、200 条；完整旧快照和 JSON v2 恢复限制为 32 MiB，仍只接受本机同源请求；
- 错误日志不打印完整事件、句子、写作、录音、Token 或 API Key；
- 数据库路径不能由请求参数指定。

如果以后需要手机通过局域网同步，必须另行设计设备配对和鉴权；第一阶段不能为了方便直接开放数据库写接口。

第一阶段 SQLite 文件不增加应用层加密，安全性依赖 Windows 用户账户和磁盘权限。写作原文、口语转写或其他敏感长文本进入总账前，必须重新评估加密和最小化保存范围。

## 14. 故障场景

| 场景 | 正确结果 |
| --- | --- |
| Node 没启动 | 事件留在浏览器待同步，页面刷新后仍存在 |
| SQLite 正忙 | 本批不确认，稍后重试，不重复更新页面进度 |
| 批次中一条格式错误 | 整批不写；隔离坏事件后重发其他合法事件 |
| SQLite 已提交但响应丢失 | 重发得到 duplicate 确认，只计一次 |
| 同一编号内容不同 | 返回冲突，保留双方，不自动挑“较新”覆盖 |
| localStorage 更新失败 | 事件仍在，启动修复投影并明确提示 |
| IndexedDB 事务失败 | 不更新 localStorage，不显示保存成功 |
| 两个标签页同时写 | UUID 去重；投影按事件顺序和版本重建 |
| 电脑时间错误 | 保留原发生时间并标记质量问题，不偷偷修正历史 |
| SQLite 文件损坏 | 隔离原文件，从校验备份恢复，再由浏览器补交 |
| 导入 JSON 中途失败 | 所有已改模块回滚，保留导入前数据 |
| 恢复旧版本代码 | 关闭新同步通道，旧 localStorage 和现有页面仍可用 |
