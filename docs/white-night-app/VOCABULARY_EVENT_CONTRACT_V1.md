# Vocabulary 学习事件契约 v1

> 状态：第一阶段已确认契约  
> 适用范围：Reader 查词、情境猜词、Vocabulary 收词与复习  
> 当前实施：Phase 2 已接入 Reader 成功查词、缺词、明确加入生词本和待确认词元；Vocabulary 复习影子写入继续运行；FSRS 与 Agent 尚未接入
> 上位蓝图：[`READER_VOCABULARY_LEARNING_DATA_BLUEPRINT.md`](./READER_VOCABULARY_LEARNING_DATA_BLUEPRINT.md)
> 本机迁移：[`BROWSER_SQLITE_DUAL_WRITE_PLAN_V1.md`](./BROWSER_SQLITE_DUAL_WRITE_PLAN_V1.md)

## 1. 大白话结论

以后系统不再只保存“这个词现在看起来会不会”，还会保存“哪一天、在哪句话里、做了什么、结果怎样”。这样换数据库、加服务器或让 Agent 分析时，可以重新算出当前状态，而不是依赖一个可能被覆盖的数字。

本契约固定两个地基：

1. 同一个词元怎样得到稳定身份；
2. 第一阶段每次词汇学习行为怎样形成可校验、可去重、可更正的事件。

## 2. 已确认边界

- 同译同学只提供产品灵感，不读取它的 `wordlist.json`，也不预留专用身份或事件。
- 查词历史和正式生词本是两类事实，查过不等于已加入复习。
- 原始学习事件、算法派生状态、AI 待验证证据和 Agent 推断必须分开。
- 事件是历史权威；`mastery`、`nextReview` 和页面统计是可重建结果。
- 第一阶段仍以浏览器本地功能可用为前提；数据库、Node 或在线 AI 不可用时不能阻断学习。
- 这是领域数据契约，不是数据库表结构；本机 SQLite 的物理实现以迁移方案为准，未来正式服务器数据库仍未指定。

## 3. 词元身份契约

### 3.1 正式词元键

正式身份格式：

```text
lexemeKey = ru:<规范原形>|<标准化词性>
```

示例：

```text
ru:идти|verb
ru:мир|noun
ru:готовый|adjective
```

`lexemeKey` 是业务身份，不是数据库自增编号。迁移到另一台电脑或未来服务器后，同一词元仍应得到同一个键。

### 3.2 原形规范化

生成正式键时按固定顺序处理：

1. 转为 Unicode NFC 形式；
2. 去掉首尾空白，并把连续空白折叠为一个普通空格；
3. 转为小写；
4. 去除单独标出的重音符号；
5. 保留正常拼写中的连字符；
6. **必须保留 `ё`，不得在正式键中改成 `е`**。

`ё → е` 只产生宽松搜索别名。例如搜索 `все` 可以找到 `всё`，但二者不能因此拥有相同正式身份。

### 3.3 标准化词性

第一版正式词性值如下：

| 值 | 含义 |
| --- | --- |
| `noun` | 名词 |
| `verb` | 动词 |
| `adjective` | 形容词 |
| `adverb` | 副词 |
| `pronoun` | 代词 |
| `numeral` | 数词 |
| `preposition` | 前置词 |
| `conjunction` | 连词 |
| `particle` | 语气词或小品词 |
| `interjection` | 感叹词 |
| `predicative` | 状态词或无人称谓语词 |
| `other` | 词典明确认定但不属于以上类别的词元 |

形动词、副动词等形态应尽量归到其词典原形及词典词性，而不是仅凭页面形态建立新词元。`other` 不能用来掩盖“不知道词性”；不知道时必须进入待确认流程。

### 3.4 不能确定时

只要原形或词性任一项不可靠，就不创建正式 `lexemeKey`，而是创建稳定的 `unresolvedLexemeId`，保存页面词形、候选项、上下文和来源。

确认后追加 `lexeme_resolution_confirmed` 事件，将先前证据归入正式词元。不得悄悄修改旧事件，也不得在确认前把证据计入某个正式词元的掌握估计。

### 3.5 释义身份

一个 `lexemeKey` 下可以有多个释义单元：

```text
lexemeKey: ru:идти|verb
senseId:   稳定随机标识
```

- `senseId` 在首次创建释义单元时生成，之后保持不变；
- 不从中文释义文字计算 `senseId`，因为文字可以修订；
- 同义改写不创建新 `senseId`；确实不同的含义才创建新释义单元；
- 暂时无法判断具体释义时，只关联 `lexemeKey`，不强行填写 `senseId`。

极少数“同原形、同词性但实际是不同词元”的同形词，未来可以增加稳定区分符。第一阶段不凭中文释义自动拆分。

### 3.6 旧键迁移

现有纯原形键或 `lemma|partOfSpeech` 键属于旧身份：

- 保留为 `legacyAlias`，用于追溯和去重；
- 能可靠确定原形与词性时映射到正式 `lexemeKey`；
- 一个旧键对应多个候选时进入待确认，不静默合并；
- 迁移不能覆盖原例句、来源、学习状态或用户笔记。

## 4. 共同事件外壳

每条事件都使用以下逻辑结构。示例中的字段名是契约名称，后续数据库可以采用不同物理布局，但含义不得改变。

```json
{
  "schema": "belye-nochi-learning-event",
  "schemaVersion": 1,
  "eventId": "018f-example-uuid",
  "learnerId": "local-learner-id",
  "deviceId": "local-device-id",
  "eventType": "dictionary_lookup_succeeded",
  "occurredAt": "2026-08-16T10:30:00.000+08:00",
  "recordedAt": "2026-08-16T10:30:00.120+08:00",
  "receivedAt": null,
  "source": {
    "module": "reader",
    "contentId": "stable-content-id",
    "location": { "chapterId": "chapter-1", "sentenceId": "sentence-8" }
  },
  "subject": {
    "surfaceForm": "шёл",
    "lexemeKey": "ru:идти|verb",
    "unresolvedLexemeId": null,
    "senseId": null,
    "reviewUnitId": null
  },
  "context": {
    "sentenceSnapshot": "Он шёл домой.",
    "meaningSnapshot": "走，步行"
  },
  "evidence": {
    "kind": "objective",
    "strength": "neutral",
    "quality": "accepted"
  },
  "payload": {},
  "correctsEventId": null
}
```

### 4.1 所有事件的必填规则

| 字段 | 规则 |
| --- | --- |
| `schema` | 固定为 `belye-nochi-learning-event` |
| `schemaVersion` | 第一版固定为整数 `1` |
| `eventId` | 全局唯一且生成后不变；同步重试必须复用原编号 |
| `learnerId` | 当前由本机自动生成；不要求注册账号 |
| `deviceId` | 由设备自动生成；重装或迁移时必须允许追溯来源 |
| `eventType` | 只能使用本契约登记的类型 |
| `occurredAt` | 行为实际发生时间，带时区的 ISO 8601 时间 |
| `recordedAt` | 本机完成持久保存的时间 |
| `receivedAt` | 后端或本地总账收到的时间；尚未同步时为 `null` |
| `source.module` | `reader`、`vocabulary`、`writing`、`speaking`、`migration` 或后续登记值 |
| `subject` | 必须指向正式词元或待确认词形，两者不能同时为空 |
| `context` | 只保存理解该事件所需的最小快照，不复制整本教材 |
| `evidence` | 明确证据种类、强度和质量；不能只靠 `payload` 猜测 |
| `payload` | 该事件特有的客观结果 |
| `correctsEventId` | 普通事件为 `null`；更正事件指向被修正事件 |

### 4.2 证据分类

`evidence.kind` 第一版取值：

- `objective`：系统可直接确认的行为或结果；
- `learner_confirmed`：学习者主动选择、确认或修正；
- `algorithm_derived`：可解释规则计算出的结果；
- `ai_unverified`：AI 产生、尚未被其他证据印证的判断。

`evidence.quality` 第一版取值：

- `accepted`：当前可参与相应计算；
- `disputed`：题目、答案或归因有争议，暂不参与可靠掌握计算；
- `corrected`：已被后续更正事件替代；
- `excluded`：因重复、损坏或验证失败而排除。

`strength` 表示这类证据在领域上的默认强弱，不是最终分数。精确权重由后续算法契约决定。

## 5. 第一阶段事件目录

### 5.1 Reader 事件

| `eventType` | 什么时候记录 | `payload` 至少包含 |
| --- | --- | --- |
| `dictionary_lookup_succeeded` | 词典成功显示结果并通过短时去重 | 查询词形、匹配方式、展示释义、是否进入先猜模式 |
| `dictionary_lookup_missed` | 查询已发起但没有可用词典结果 | 查询词形、失败类别、候选原形；不得提升或降低掌握 |
| `reading_exposure_observed` | 句子满足可见、页面活动和停留条件 | 可见位置、有效停留、会话去重键；默认很弱证据 |
| `context_guess_completed` | 学习者完成先猜题 | 两句语境、三个选项、所选答案、参考答案、是否正确、题目来源 |

成功查询和失败查询互斥。点击发生但尚未得到词典结果时，不提前写入成功事件。

Phase 2 当前采用 15 秒短时去重窗口：同一词元或待确认对象、同一来源位置、同一句子和同一结果类型在窗口内只保留一条事件。加载尚未完成、词典资源加载失败和联网请求报错不记成缺词；本地词典完整加载后仍无结果才记缺词。该秒数是可调整的实现参数，不改变事件身份与去重原则。

### 5.2 Vocabulary 事件

| `eventType` | 什么时候记录 | `payload` 至少包含 |
| --- | --- | --- |
| `vocabulary_entry_added` | 学习者明确加入正式生词本 | 加入方式、初始目标释义、关联查词事件 |
| `vocabulary_entry_pending_resolution` | 学习者明确保存了尚不能可靠确定原形或词性的词形 | 加入方式、关联查词事件、候选原形；不得进入正式掌握计算 |
| `review_attempt_completed` | 一次复习作答完成 | 测试方式、题目快照、作答快照、原始结果、答案是否在作答前揭示、提示类型、反应时间、同日序号、距上次间隔 |
| `vocabulary_entry_graduated` | 算法判定暂时退出日常复习 | 算法版本、使用的证据编号、毕业原因 |
| `vocabulary_entry_reactivated` | 新证据使词条重新进入复习 | 触发事件、算法版本、重新进入原因 |

`vocabulary_entry_added` 不能由“查过一次”自动代替。毕业和重新进入是可逆队列状态，不等于删除词条或历史。

任何可能参与长期调度的复习事件都必须填写 `subject.reviewUnitId`。事件保存原始作答事实；`是否属于有效回忆` 和 `Again / Hard / Good` 是带算法版本的派生结果，不能为了方便重放而删掉原始答案、揭示状态和提示信息。

### 5.3 解析、使用和更正事件

| `eventType` | 什么时候记录 | `payload` 至少包含 |
| --- | --- | --- |
| `lexeme_resolution_confirmed` | 待确认词形被可靠归入正式词元 | `unresolvedLexemeId`、目标 `lexemeKey`、确认者、依据事件 |
| `usage_evaluated` | 写作或口语中某个实际用法被评价 | 使用快照、评价结果、评价来源、关联释义；AI 评价必须标为待验证 |
| `evidence_corrected` | 旧事件的答案、归因、词元或质量需要修正 | 被修正字段、旧值摘要、新值、修正原因 |

`evidence_corrected.correctsEventId` 必填。更正后旧事件仍用于审计，但派生计算采用更正后的有效解释。

### 5.4 隐私永久删除

隐私删除不是普通学习结果，分成命令和审计结果：

1. `privacy_erasure_requested`：学习者要求删除指定私人正文、录音、转写或事件范围；
2. 系统从当前数据、同步副本和受管备份中清除目标内容；
3. 写入 `private_content_erased` 审计事件，只保留删除范围、完成时间和结果，不得保留被删原文。

这是真正删除规则，是“事件通常只追加”的明确例外。无法自动清理的离线导出文件必须提示学习者手动处理，不能宣称已全部删除。

## 6. 写入与同步规则

### 6.1 只追加和幂等

- 已保存事件不原地覆盖；普通变化产生新事件；
- 同一行为的同步重试复用同一 `eventId`；
- 接收方发现已有相同 `eventId` 时返回成功但不重复计数；
- 不以时间戳或词元键代替事件编号，因为同一词可以在不同时间真实学习多次。

### 6.2 时间含义

掌握和复习间隔按 `occurredAt` 计算；同步延迟按 `receivedAt` 观察。设备时间明显异常时标记数据质量问题，不静默改写发生时间。

### 6.3 离线优先

浏览器先在本地持久保存事件，再更新页面。未来总账不可用时事件进入待同步队列；恢复后补交。是否同步成功不能决定这次学习行为是否在本机生效。

### 6.4 最小内容快照

事件保存当时判断必需的句子、选项、作答和释义，不保存整章副本。录音、长写作和其他大体积私人内容使用独立内容标识，事件只引用它并记录必要摘要。

## 7. 当前状态是投影，不是第二份事实

下列内容都是根据有效事件计算或整理出的“当前视图”：

- 正式生词本列表；
- 查词次数与最近查词时间；
- 各释义单元和词形的掌握估计；
- 下次复习时间；
- 今日任务；
- 毕业或重新进入状态。

页面可以缓存这些视图以提高速度，但必须记录所用算法版本和最后处理的事件位置。缓存损坏时，应能从事件和合法迁移快照恢复，不能生成一套互不兼容的新进度。

掌握估计、复习单元、合格长期回忆和调度参数以 [`VOCABULARY_MASTERY_SCHEDULING_CONTRACT_V1.md`](./VOCABULARY_MASTERY_SCHEDULING_CONTRACT_V1.md) 为准。

过渡期的 `vocabulary-review-records` 等现有结构只是兼容投影；在新事件链验收完成前仍保留，不能突然删除或降级。

## 8. 旧浏览器数据迁移

旧数据通常只保存当前 `mastery`、`nextReview`、有限 `history` 和词条内容，无法还原每一次真实行为。因此：

1. 原样备份旧数据；
2. 校验后创建 `legacy_vocabulary_snapshot_imported` 迁移事件；
3. 快照保存旧状态、来源键、导入时间和映射结果；
4. 不能把一个总分伪造成多条历史复习事件；
5. 从导入完成之后开始记录真实逐次事件；
6. 映射不确定的词条进入待确认，不覆盖现有内容；
7. 双写核对期结束前，旧浏览器记录继续保留。

`legacy_vocabulary_snapshot_imported` 只允许 `source.module = migration`，不参与第一阶段普通页面直接写入。

## 9. 最小校验要求

事件被接受前至少验证：

- 公共必填字段存在且类型正确；
- `schemaVersion` 和 `eventType` 受支持；
- 时间合法且带时区；
- 正式词元与待确认词形满足互斥规则；
- `lexemeKey` 能通过同一套规范化规则重新得到相同结果；
- 事件特有的必填 `payload` 齐全；
- AI 结果没有被标为 `objective`；
- 更正事件确实引用存在或可延后解析的旧事件；
- 同一 `eventId` 的重复内容完全一致；若编号相同但内容不同，必须报冲突；
- 私人内容没有进入禁止保存或导出的字段。

校验失败的导入必须整体回滚，不能只导入一半。实时写入失败必须明确留在待处理状态，不能让页面显示“已保存”而实际丢失。

## 10. 验收样例

实现本契约时，至少用以下场景做自动化测试：

1. `ёлка` 和 `елка` 可以互相宽松搜索，但正式身份不被静默折叠；
2. 同原形、不同词性的条目不会合并；
3. `стали` 在 `стать` 与 `сталь` 之间不确定时只生成待确认记录；
4. 待确认记录归入正式词元后，原事件仍可追溯；
5. 同一查词事件重复同步两次只计一次；
6. 同一词在不同时间真实查询两次保留两条事件；
7. 修改中文释义不改变 `senseId`；
8. AI 生成题被标记有争议后，不再参与可靠掌握计算；
9. 旧总分只导入为快照，不产生虚构复习次数；
10. 数据库或 Node 不可用时，本地事件仍能保存并在恢复后补交；
11. 隐私删除后，当前数据和受管备份不再包含目标原文；
12. JSON 导入失败时原有学习数据完整保留。

## 11. 尚未决定的实现参数

以下内容不属于本次地基决定，后续必须另行设计和验证：

- 查词短时去重窗口是否需要根据真实使用从当前 15 秒调整；
- 阅读接触的可见比例、停留时间和去重窗口；
- 非词汇模块是否复用同一套掌握算法；
- 第二备份位置的选择方式和应用层加密范围；
- 服务器、账号、鉴权、多用户和云同步方案；
- 如何展示或请求学习者处理词元与释义歧义。

这些参数可以改变，但不得破坏本契约已经固定的身份、历史、更正、离线和迁移原则。
