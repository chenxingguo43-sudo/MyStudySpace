# 白夜俄语 Agent 基础产品与架构定义

> 状态：已确认 v1.0
> 文档性质：本项目的上位事实来源（Foundation / Architecture Charter）
> 当前阶段：基础架构与实验边界已确认；准备先验证 Penguin-Harness、再验证 DeepTutor；尚未授权生产实现、提交或推送

## 0. 文档目的与优先级

本文件先回答一个最基础的问题：**白夜俄语究竟是什么，Reader、DeepTutor 与 Penguin-Harness 分别处于什么位置。**

本文件已确认。下一阶段先完成Penguin-Harness和DeepTutor两轮受控验证；两轮验证结束并锁定运行边界后，再恢复UI细化。

若本文件与以下旧文档冲突，以本文件和用户最新明确指令为准：

- `DEEPTUTOR_FORK_VALIDATION_PLAN.md`（当前受控实验计划）
- `READER_DEEPTUTOR_INTEGRATION_HANDOFF.md`
- 任何把 DeepTutor 作为第二个运行 Agent、嵌入模块或生产依赖的旧描述

现有 Reader → DeepTutor 手动复制粘贴桥接是已存在的过渡能力，但**不是目标产品架构**。

## 1. 一句话定义

> **白夜俄语是一个长期私人俄语学习 Agent / 综合私人导师：每天根据用户的真实学习状态，决定接下来学什么，并主动推动学习持续完成。**

当前真实阶段目标是：

> 从正式入学诊断第 1 天开始，在一个 90 天周期内准备并通过 ТРКИ-2 / TORFL B2。

90 天 B2 只是当前可替换的阶段目标。完成、暂停或更换该目标后，白夜俄语仍应继续服务于口语、C1、实际交流、听力、文学阅读、专业俄语、维持、词汇扩展或无固定期限的长期学习。

## 2. 单 Agent 原则

### 2.1 最终产品只有一个 Agent

最终用户面对的唯一产品 Agent 是：

```text
白夜俄语 Agent
```

导师问答、讲解、复盘、练习生成、学习记忆、目标、画像和规划都属于白夜俄语 Agent 自身，不存在面向用户的“双 Agent 产品”。

### 2.2 明确禁止的目标架构

不得把目标系统实现成：

```text
白夜俄语 Agent
    ↓ iframe / API / 页面跳转 / 共享工作区
DeepTutor Agent
```

不得：

- 把 DeepTutor 当作白夜俄语内部运行的第二个 Agent；
- 把完整 DeepTutor 页面嵌入白夜俄语；
- 要求生产环境同时启动独立 DeepTutor 进程；
- 让 DeepTutor 与白夜俄语各持有一套相互竞争的画像、记忆和规划；
- 让白夜俄语的核心学习闭环依赖 DeepTutor 在线；
- 把 Penguin-Harness包装成第二个面向用户的 Agent。

### 2.3 “使用上游代码”不等于“运行第二个 Agent”

白夜俄语可以研究、Fork、移植或改写 DeepTutor 和 Penguin-Harness 的代码，但最终采用的代码必须进入白夜俄语自己的产品边界、数据边界和发布边界。

## 3. 四个核心角色

```text
DeepTutor 实验 Fork ──┐
                      ├──> 构建唯一的白夜俄语 Agent <── Reader / 未来客户端
Penguin-Harness ──────┘
```

### 3.1 白夜俄语 Agent：唯一产品主体

白夜俄语拥有：

- 目标与阶段；
- 客观证据接收和索引；
- 派生学习画像；
- 每日、每周和阶段计划；
- 规则引擎与计划校验器；
- 导师问答、讲解、苏格拉底追问与迁移练习；
- 学习记忆和长期偏好；
- 任务状态和计划版本；
- 材料目录；
- 后台调度；
- 离线同步与未来多设备状态；
- AI 不可用时的降级逻辑。

### 3.2 Reader：可替换的练习与证据客户端

Reader负责：

- 教材练习；
- 阅读、听力、词汇、口语和写作等训练入口；
- 本地即时保存客观学习事件；
- 计时与活动/成果证据；
- 离线 outbox；
- 向白夜俄语 Agent 同步原始证据；
- 展示并执行 Agent 下发的计划。

Reader不是长期产品核心。即使未来重写、替换或停用 Reader，白夜俄语的目标、证据、画像、计划历史和长期记忆仍应保留。

### 3.3 DeepTutor：导师能力实验上游

DeepTutor不是第二个生产 Agent。采用路线 C：

```text
严格受控的 DeepTutor 实验 Fork
    ↓
验证导师相关能力
    ↓
形成“采用 / 适配 / 重写 / 放弃”清单
    ↓
将选定能力移植或重构进白夜俄语 Agent
    ↓
实验 Fork 退出生产路径
```

实验 Fork：

- 不持有正式用户数据；
- 不作为白夜俄语的生产依赖；
- 不做正式产品 UI；
- 不无限扩展为第二套产品；
- 必须有范围、验收指标、时间边界和退出条件。

### 3.4 Penguin-Harness：帮助构建白夜俄语 Agent 的 Harness 与候选底座

Penguin-Harness不是第二个产品 Agent。它的角色是帮助构建、运行、评测和改进白夜俄语 Agent。

优先评估和选择性采用：

- Core Agent 执行循环；
- OmniMessage 协议思想；
- LLM 与 Environment 接口；
- Session 生命周期；
- Trace 审计与回放；
- Skills 机制；
- Benchmark、Scoreboard、Snapshot 与回滚机制；
- Server 常驻、SSE、调度等通用能力。

白夜俄语必须自行拥有或重构：

- 学习事件；
- 90 天和长期阶段目标；
- 学习画像；
- 每日计划；
- 计划校验；
- 学习材料模型；
- Reader 同步；
- 多设备与离线模型；
- 产品 UI。

Penguin 的通用 Goal Mode、Agent State 和 Trace 不得直接冒充白夜的阶段目标、学习画像和学习证据。

## 4. 目标模块边界

### 4.1 白夜长期阶段目标

白夜的目标是可持久化、可替换、可暂停、可完成并保留历史的学习阶段对象，例如：

- 90 天通过 TORFL B2；
- 强化口语；
- 准备 C1；
- 提升文学阅读；
- 无截止日期的长期维持。

它包含：

- 起止条件；
- 五科或能力范围；
- 负荷约束；
- 诊断和验收节点；
- 风险；
- 计划版本；
- 历史状态。

### 4.2 Penguin Goal Mode

Penguin Goal Mode是一次 Agent 运行中的持续执行协议，用于让模型持续工作直到 `complete`、`blocked` 或预算终止。

它可以用于后台工程任务或受控 Agent 工作，但：

```text
Penguin Goal Mode ≠ 白夜学习阶段目标
```

白夜阶段目标不得仅保存为 `GOAL.yaml` 或依赖单次 Session 存活。

## 5. 数据权威与可追溯性

### 5.1 原始学习事件

Reader和未来客户端产生的原始学习行为采用追加事件模型：

```json
{
  "eventId": "uuid",
  "deviceId": "local-reader-01",
  "eventType": "answer_submitted",
  "occurredAt": "...",
  "receivedAt": "...",
  "source": "reader",
  "payload": {}
}
```

原则：

- `eventId` 全局唯一；
- 服务端幂等接收；
- 原始证据只追加，不被画像或同步冲突覆盖；
- Reader离线时写入 IndexedDB 和 outbox；
- 恢复连接后自动重试；
- 重复同步不得重复计时或重复计分；
- 派生画像可以重建；
- 同一计划可变字段的并发修改单独处理冲突。

### 5.2 学习画像

白夜 Agent根据原始事件计算：

- 五科状态；
- 知识点掌握；
- 置信度；
- 疲劳；
- 优先级；
- 错误模式；
- 下一步建议。

每条结论必须区分：

- 客观事实；
- 用户确认；
- Agent推断；
- 导师判断；
- 人工复核。

### 5.3 Agent Trace

Penguin式Trace可用于记录：

- 模型请求与输出；
- 工具调用；
- 计划生成过程；
- 导师对话；
- 失败、重试和审批；
- Benchmark运行。

但：

```text
Agent Trace = 运行审计
学习事件存储 = 学习事实
```

两者不得混为同一事实来源。

### 5.4 记忆原则

最终白夜只有一套产品级长期学习记忆。DeepTutor实验记忆不得成为正式记忆源；实验结果进入白夜前必须转化为白夜自己的结构化数据或明确来源的导师结论。

## 6. 单体模块边界

第一版是一个独立部署的轻量模块化单体，不拆成微服务群：

```text
white-night-agent/
├─ runtime/          # Agent运行内核适配
├─ goals/            # 阶段目标
├─ evidence/         # 事件接收、幂等、索引
├─ profile/          # 派生画像
├─ planning/         # 日/周/阶段规划
├─ validator/        # 计划硬约束校验
├─ tutor/            # 导师能力
├─ memory/           # 长期学习记忆
├─ materials/        # 材料目录
├─ scheduling/       # 后台调度
├─ sync/             # outbox协议与未来多设备同步
├─ providers/        # LLM/STT/TTS等外部服务适配
├─ api/              # 客户端API
└─ web/              # 白夜产品UI（基础文档确认后再设计）
```

模块边界不等于微服务。第一版可以在一个进程、一个部署单元和一个轻量数据库中运行。

## 7. 规划与导师协作

### 7.1 规则与 LLM 分工

计划生成采用：

```text
规则硬约束 + LLM教学判断 + 计划校验器
```

规则负责：

- 截止日期和阶段节点；
- 每周负荷；
- 五科覆盖；
- 间隔复习；
- 模考节点；
- 任务依赖；
- 疲劳和负荷上限；
- 材料真实性；
- 缺勤重排。

LLM负责：

- 教学判断；
- 错因分析；
- 任务选择建议；
- 推荐理由；
- 苏格拉底追问；
- 迁移练习；
- 写作和口语定性反馈。

所有LLM计划提议必须通过计划校验器，不能直接覆盖有效计划。

### 7.2 导师能力属于白夜

白夜 Tutor模块负责：

- 自由俄语问答；
- 讲解；
- 苏格拉底追问；
- 错误模式复盘；
- 迁移练习；
- 练习生成；
- 写作和口语定性反馈；
- 将导师结论以明确来源写回白夜数据模型。

DeepTutor实验仅用于发现哪些实现值得采用，不在生产运行时承担这些职责。

## 8. 当前90天学习约束

当前阶段：

- 目标：通过正式 ТРКИ-2 / TORFL B2；
- 周期：从完整入学诊断第1天起90个自然日；
- 起点：语法词汇、阅读、听力、写作、口语均未知；
- 诊断：前两天完成主要五科诊断，第一周继续校准；
- 正式基线：第7天形成首次基线和风险判断；
- 高强度日：每周6天，每天8小时净学习；
- 恢复训练日：每周1天，2—4小时净学习；
- 第一周逐步爬坡；
- 有效时间必须同时有计时与活动/成果证据；
- 未完成任务按价值重排，不机械累积成时间债。

写作和口语当前只做明确标注的定性AI反馈，不给未经校准的精确考试分数或通过概率。

## 9. 材料原则

材料采用分层目录：

1. 本地结构化材料；
2. 用户合法导入的书、试题和音频；
3. 官方公开样题（用于诊断和验收）；
4. 经过审核的公开网络资源；
5. 明确标记的AI生成追诊或迁移内容。

禁止虚构：

- 材料；
- 链接；
- 页码；
- 题号；
- 官方身份；
- 精确个性化结论。

证据或材料不足时必须明确降级，不得伪装为精确推荐。

## 10. 运行与部署

### 10.1 本机阶段

先在本机完成独立Agent闭环：

```text
Reader          http://localhost:3000
白夜俄语 Agent  http://localhost:3100（规划值，尚未实现）
```

DeepTutor实验Fork可以在隔离的开发环境中运行，但不属于目标本机产品拓扑。

### 10.2 服务器阶段

未来迁移到约4GB RAM服务器：

- Agent服务、API、规则、调度和轻量持久化在服务器；
- 大型LLM、STT和TTS优先使用外部服务；
- 不假设服务器可以承载大型本地模型、重型语音模型或大型向量基础设施；
- 数据、私有配置和服务应可从本机迁移，而非重新设计。

### 10.3 第一版多设备边界

第一版先实现本机单设备闭环，但从第一天按未来多设备标准设计：

- 标准事件；
- `eventId`；
- 预留 `deviceId`；
- outbox；
- 幂等；
- 设备无关API；
- 计划版本。

第一版不要求真实登录、跨网访问、手机端、录音上传和复杂冲突UI。

## 11. MVP核心闭环

```text
Reader产生客观学习事件
  ↓
本地立即保存并进入outbox
  ↓
白夜Agent幂等接收
  ↓
建立最小可用画像
  ↓
规则 + LLM提出计划
  ↓
计划校验器验证
  ↓
保存计划版本
  ↓
Reader或白夜客户端读取并执行
  ↓
完成证据返回
  ↓
Agent动态重排
```

MVP必须：

- 读取Reader证据；
- 建立最小画像；
- 生成真实、可执行的今日计划；
- 记录计划、计时、输出和完成；
- 接收返回证据；
- 动态重排；
- 保存计划版本；
- 在AI导师能力不可用时继续安全学习。

---

## 12. AI失效与降级

降级顺序：

1. 规则 + LLM；
2. 纯规则计划；
3. 最近有效计划中的安全任务；
4. 到期复习、错题练习、自由学习入口；
5. 恢复后接收离线证据并重新规划。

UI必须显示当前模式和原因。任何降级都不得丢弃或覆盖离线学习证据。

## 13. Penguin-Harness技术验证清单

第一轮时间盒：**3个开发日**。它先于DeepTutor实验进行，只使用固定测试样例和脱敏/模拟数据。计划实验目录为 `experiments/penguin-harness-lab/`，默认不纳入主仓库提交。

固定Benchmark采用现有Reader复盘包结构的模拟版本：3组样例（单一语法错误、跨题重复错误、证据不足降级），输入为10道结构化作答证据，输出为中文讲解、必要的俄语例句/问题、2个苏格拉底问题和1道不泄露答案的迁移题。硬约束必须全部通过，教学质量平均至少4/5。

在决定把Penguin代码作为白夜生产依赖前，至少验证：

1. `penguin-core`能否独立于完整Web/Desktop运行；
2. Session、流式消息、工具调用、审批、中断和恢复是否稳定；
3. LLM接口能否接入计划中的模型供应商；
4. Trace能否与白夜学习事件存储清晰隔离；
5. Skills能否表达俄语Tutor行为且不污染领域数据；
6. Benchmark能否评测计划和Tutor行为；
7. Snapshot与回滚是否只影响Agent定义，不影响用户证据；
8. Server、Scheduler和SQLite边界能否适配白夜的模块化单体；
9. Node >=24、pnpm和依赖对本机及未来4GB服务器的影响；
10. 基础内存、空闲内存、单Session峰值、并发与长期运行稳定性；
11. Apache-2.0归属、NOTICE和修改记录要求；
12. 上游升级和退出成本。

每一项最终标记：

```text
采用 / 适配 / 重写 / 放弃
```

退出标准：如果核心包不能独立、资源不合适、数据边界冲突、升级成本过高或必须引入大量无关功能，则白夜不得被绑定在Penguin上；可以只保留设计借鉴和Benchmark方法。

## 14. DeepTutor实验Fork验证清单

第一轮时间盒：**3个开发日**。它在Penguin-Harness第一轮验证之后进行，定位为可行性筛查；只使用与Penguin相同的固定测试样例、同一个可用LLM和脱敏/模拟数据，不接入Reader正式数据。计划实验目录为 `experiments/deeptutor-fork-lab/`，默认不纳入主仓库提交。

第一轮只验证与俄语导师直接相关的能力，不做完整产品Fork：

- 结构化学习证据输入；
- 跨题错误模式识别；
- 将推断标为“待确认”；
- 苏格拉底追问；
- 迁移练习生成；
- 自由俄语问答；
- 练习生成；
- 写作和口语定性反馈；
- 对话记忆与长期学习记忆的可分离性；
- Skills或等效机制；
- 模块独立性；
- 资源占用；
- Python依赖和迁移到最终白夜架构的成本。

不在第一轮验证：

- Research；
- Visualize；
- Partners；
- 视频与图像生成；
- 大型通用知识中心；
- 完整DeepTutor UI；
- 多用户商业功能；
- 深度双向Reader桥接。

实验结束必须产出：

- 采用清单；
- 适配清单；
- 重写清单；
- 放弃清单；
- 性能测量；
- 俄语能力评测结果；
- 迁移建议；
- 退出决定。

退出标准：如果模块高度耦合、资源过重、俄语适配价值低或移植成本高于重写，则停止继续Fork，不因已投入成本把DeepTutor带入生产。

---

## 15. 受控评测与自我改进

Penguin式Benchmark可以用于评测：

- 是否识别真实错误模式；
- 是否区分事实与推断；
- 是否遵守苏格拉底数量限制；
- 是否生成不泄露答案的迁移题；
- 是否引用真实材料；
- 是否违反时间、负荷和五科覆盖约束；
- 是否在证据不足时正确降级；
- 是否在LLM不可用时提供安全计划。

自我改进只能修改受控的Agent定义、Prompt、Skill或候选配置，并且：

- 必须有固定Benchmark；
- 必须保留基线；
- 必须可审计；
- 必须Snapshot；
- 分数不提升则回滚；
- 不得修改正式用户证据；
- 不得未经用户确认自动发布到生产；
- 不得自动放宽计划硬约束。

---

### 15.1 已确认的第一轮评测协议

- 3组固定模拟样例，每组在每个框架中重复3次，共9次输出；
- Penguin与DeepTutor使用同一模型、同一参数和同一测试集；
- 数量、字段、禁令等硬约束由脚本检查；
- 教学质量由人工审阅，LLM评委只作辅助；
- A/B匿名审阅，隐藏框架名称；
- 教学质量维度：俄语正确性、解释清晰度、教学针对性、下一步可执行性；
- 通过标准：9次全部通过硬约束；教学质量总平均至少4/5，任何一次不得低于3/5；
- 记录延迟、输入/输出Token和估算模型费用；
- 日志可保留固定模拟输入与输出，但必须遮蔽密钥、Authorization头和本机私密路径；
- 实验结束后保留Benchmark、评分、资源报告和决策矩阵；不再需要的实验Fork/克隆归档或移除。

## 17. UI前置约束

基础文档确认前暂停UI细化。恢复UI后，UI必须体现：

- 用户只看到一个白夜俄语Agent；
- Reader是训练客户端，不是产品核心；
- 不出现需要用户理解的DeepTutor或Penguin内部产品边界；
- 今日计划和当前任务优先；
- 完整计划可见；
- 证据来源、置信度和降级模式可见；
- Agent建议强但用户可覆盖；
- 计划不会因刷新或新证据静默覆盖；
- 离线学习可继续。

此前UI讨论中仍可保留的方向，需在本文件确认后重新审查：

- 独立白夜俄语产品首页；
- 按学习流程组织导航；
- 今日双栏控制台；
- 专注任务模式；
- 分层复盘；
- 分层证据画像。

此前把DeepTutor作为“导师页”“深度工作区”或跳转目标的描述失效。

## 19. 当前已锁定结论

1. 产品名是“白夜俄语”。
2. 最终产品只有一个白夜俄语Agent。
3. 导师能力属于白夜俄语Agent自身。
4. Reader是可替换的练习与证据客户端。
5. DeepTutor采用路线C：实验Fork验证后选择性移植或重构，不作为生产依赖。
6. Penguin-Harness用于帮助构建白夜俄语Agent，并只选择性评估通用Harness能力。
7. 白夜自己拥有目标、证据、画像、计划、长期记忆和数据权威。
8. 第一版是独立部署的轻量模块化单体，不是微服务群。
9. 先在本机运行，未来迁移约4GB服务器。
10. 第一版先做单设备闭环，但按未来多设备和离线同步标准设计。
11. 当前阶段是包含诊断在内的90天TORFL B2计划。
12. 先确认本基础文档，再恢复UI讨论。
13. 未经用户明确确认，不提交、不推送，也不开始生产实现。
14. Penguin-Harness第一轮验证为3个开发日，先于DeepTutor实验。
15. DeepTutor第一轮实验为3个开发日，只做可行性筛查。
16. 两个实验只使用固定测试样例和脱敏/模拟数据。
17. 两个实验使用同一个经兼容性检查的私密配置模型，不在代码、文档或聊天中记录密钥。
18. 两轮实验结束并锁定运行边界后再恢复UI。
19. `experiments/`默认不纳入白夜主仓库提交；只迁入用户审核通过的结论或选定代码。
20. 词汇第一阶段使用统一词元身份、只追加学习事件和 FSRS-6 掌握调度，不以最近一次自评作为掌握真值。
21. 本机第一版使用浏览器事件账异步同步到 Node 管理的 SQLite，Node 或数据库不可用时基础学习继续。
22. SQLite 只是本机总账，不预先决定未来服务器数据库；Penguin 和 DeepTutor 实验不得连接正式学习数据。
