# Astra 指令与 Skill 整改实施方案

状态：已执行并完成静态复验  
日期：2026-09-06  
依据：`docs/ASTRA_INSTRUCTION_REMEDIATION_PLAN.md`

## 1. 方案目的

这份文件把整改计划展开成可以逐批执行的操作说明。以后真正整改时，每完成一批就检查一批，不把几十个文件一次性改完，也不覆盖用户当前正在进行的 Reader 工作。

本方案原本只设计改法。用户随后明确要求执行，相关长期指令和 Skill 已按本方案整改；没有发送本地内容给外部 AI、提交或上传。

## 2. 最终要形成的规则关系

整改后，指令关系应当简单清楚：

1. 用户当轮明确要求决定本次要做什么。
2. `AGENTS.md` 保存长期偏好、安全要求和项目事实。
3. 只有任务确实匹配时才选择一个最合适的 Skill。
4. Skill 只规定这种专用工作怎么做，不能扩大用户要求。
5. 检查程序只判断能客观确认的内容，不能替代用户对主观效果的判断。

建议在用户级 `AGENTS.md` 中加入下面这段共同总则，项目文件无需重复全文：

```md
## 指令与执行范围

- 用户当轮明确要求优先于 Skill。Skill 只补充用户没有说明的做法，不能扩大任务范围。
- 审查、解释、引用、比较或排查一个 Skill，不等于调用或执行它。
- 用户已经授权的范围持续有效。只有后续动作明显超出范围、会向外部写入、需要新凭据，或难以恢复时才再次询问。
- 能从当前文件、工具结果和对话中查清的事情自行查清。只有缺失答案会明显改变结果时才询问。
- 检查按改动影响决定。相关检查通过后，只有出现新改动、新失败或新疑点时才扩大或重复。
```

安全规则仍高于普通工作习惯，例如不得泄露密钥、不得破坏用户数据、不得擅自提交或上传。

目标文件：

### 7.1 首次试做

只有以下情况需要新的学习者验收：

- 新教材种类；
- 新教学结构；
- 新的内容生成来源；
- 数据格式或页面展示发生实质变化；
- 之前的验收明确不覆盖当前范围。

首次试做仍应检查内容、证据、电脑显示和手机显示。真正需要用户判断的是“是否容易学懂”，程序能判断的格式、缺字段和错误答案不应留给用户。

### 7.2 已验收后的续做

验收记录至少说明：

- 适用的教材或模块；
- 教学结构版本；
- 页面格式版本；
- 验收时间和结果；
- 哪些变化会使这次验收失效。

同一范围继续生产时复用验收结果，不在每批后重复询问。只有上面列出的实质变化发生时才重新做小批试做。

### 7.3 可以自动停止的情况

继续保留以下停止条件：

- 标准答案冲突；
- 原文证据找不到；
- 题目或选项对应不上；
- 受保护字段丢失；
- 页面无法读取新内容；
- 共同检查失败，继续会让更多内容出错；
- 缺少用户才能决定的教材范围或内容依据。

停止时保存已通过内容和当前状态，写清楚恢复方法。普通批次成功后继续处理，不要求用户反复说“继续”。

### 7.4 本批验证

- 新教学结构第一次运行会停在学习效果验收处；
- 已验收的相同结构自动继续下一批；
- 修改一个不影响结构的错别字不会使验收失效；
- 改变页面数据格式会重新触发小批试做；
- 标准答案冲突会停止对应内容，并保留其他已完成内容；
- 状态恢复不会重新生成输入未变化的已完成任务。

## 8. 第 5 批：整理设计类 Skill

### 8.1 共同触发边界

设计类 Skill 的 `description` 必须说明：

- 适合什么页面；
- 不适合什么页面；
- 是默认入口还是用户点名才用；
- 是否要求生成图片；
- 与现有设计、品牌和功能谁优先。

白夜俄语 Reader 是学习工具，不因“网页”“界面”两个词自动套用宣传页、作品集或 Awwwards 风格流程。

### 8.2 design-taste-frontend

## 11. 分批退回办法

每一批单独记录修改文件。若一批验证失败，只退回该批对应文件到修改前快照，再重新应用已经确认有效的小改动，不能用破坏性 Git 命令清空整个工作区。

退回优先顺序：

1. 使用该文件自己的修改前快照；
2. 对受 Git 管理且修改前干净的文件使用明确的旧内容；
3. 对原本已有用户改动的文件，用逐段补丁恢复本批变化，保留用户原有内容。

任何退回都不删除未跟踪文件，不影响 Reader 当前生产数据。
