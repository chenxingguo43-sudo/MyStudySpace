# 浏览器先记账再同步本机 SQLite

白夜俄语第一阶段先把学习事件和待同步状态原子写入浏览器 IndexedDB，再异步批量提交给本机 Node 进程管理的 SQLite；只有 SQLite 事务提交后才产生同步确认。数据库停机不能阻断 Reader 或 Vocabulary，未来服务器也必须复用同一事件身份和幂等协议，而不能用整份“最新进度”覆盖浏览器历史。

## Considered Options

- 每次操作直接写 SQLite：总账简单，但 Node 未启动时网页无法正常学习。
- 定时上传整份 localStorage：实现快，但多设备和失败重试会互相覆盖，也无法准确去重。
- 浏览器事件账加待同步队列：需要维护两个物理副本和核对机制，但能离线工作、逐事件去重并渐进迁移。

## Consequences

- 本机第一版使用 Node 24 内置 `node:sqlite`，数据库文件放在 Windows 本地应用数据目录，不进入项目仓库；这不决定未来云服务器数据库。
- 新学习行为必须先保存事件和待同步记录，再更新兼容进度；不能先显示“已保存”再尝试记事件。
- 同一 `eventId` 重传必须安全；相同编号但内容不同必须报冲突并停止整批写入。
- 现有 `/api/vocab-sync`、`/api/novel-vocab` 和 `rr_sync_fail_queue` 保持旧职责，不能当作学习事件总账。
- 本机学习数据接口只接受本机同源 JSON 请求；当前静态服务器即使监听局域网，也不能让未鉴权设备写入总账。
- SQLite 成为本机总账前必须完成连续 14 天影子核对、备份恢复和故障注入验收。
